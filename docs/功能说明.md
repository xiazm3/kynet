# kynet

JDK：Java 25。

`kynet` 是按照项目规划文档实现的分布式网游服务框架：

- `kynet-common`：协议模型、`ActionKey`、服务标识工具、Protobuf（jprotobuf）载荷编解码与零拷贝帧编解码。
- `kynet-registry`：集群化注册中心，维护实例、Action、Topic 目录和注册心跳，只处理注册发现。
- `kynet-framework`：`ServiceNode`、Action 注解与注册、`ActionContext`、`ActionResult`、`PlayerBroadcaster`、Netty 网关服务端实现。

## 当前能力

- 服务通过 `ServiceNode(host, port, serviceName)` 以 Netty TCP 连接 Registry；业务流量根据本地目录直连，同主机优先使用 Aeron IPC，跨主机使用 UDP。
- 业务服务通过 `ActionBootstrap` 注册 `@ActionController` / `@ActionMethod`。
- 调用方使用 `invoke(cmd, act, payload)` 发起单播 RPC。
- 发布方使用 `publish(topic, payload)`，订阅方使用 `subscribe(topic, subscriber)`。
- 业务服务可通过 `PlayerBroadcaster` 触发到 `GatewayService` 的内部下行消息。
- 网关服务端已支持 `tcp://`、`tcps://`、`udp://`、`ws://`、`wss://` 外部接入端点。
- 游戏客户端可通过 `gateway` 按 `cmd/act` 调用 action 并订阅服务端 push。
- 服务端权威踢人：业务可在 action 内断开当前玩家、踢掉指定用户全部连接或顶号保留新会话。
- Gateway 支持 TLS、Origin 白名单、连接容量、单 IP 连接速率、多层 QPS、协议长度边界和慢客户端策略。
- Registry 支持多节点发现、认证 Gossip、版本化目录快照和故障摘除；业务 RPC、响应、推送和事件由 ServiceNode 直连发送。

架构、部署参数、投递语义及升级步骤见 [注册发现与 Aeron 直连](docs/registry-direct-transport.md)。

## 高性能发送路径

常规 `invoke` / `invokeOneWay` 会走完整的路由、重试和响应分发逻辑。极限 IO 或状态同步路径可以使用预编码发送器：

- `ServiceNode.prepareFastOneWaySender(cmd, act, payload, options)`：预编码 one-way 帧，之后每次 `send(...)` 只写 requestId 并直接 offer。
- `ServiceNode.prepareFastRpcSender(cmd, act, payload, options)`：预编码 RPC 请求，支持 `invokeAsync()` 和回调式 `invoke(FastRpcCallback)`。
- 接收端通过 `setFastOneWayHandler(...)` 在 I/O 线程内直接拿到 `DirectBuffer` 视图。

预编码帧在发送前已预留 direct envelope 前缀；显式指定 `targetInstanceId` 时前缀只写一次。这些 API 不做业务反序列化，处理器在读线程内执行，不要在回调中做阻塞业务。直投与回退队列之间不保证严格顺序，需要有序时使用常规调用，或让每个会话只由一个线程发送。

直连数据面的线程模型和空闲策略可通过系统属性调整：

| 属性 | 默认值 | 说明 |
| --- | --- | --- |
| `kynet.direct.idleStrategy` | `yield` | `yield` 为低延迟默认值；`busy` 尾延迟最低但空闲时占满一个核；`backoff` 更省 CPU；`noop` 仅用于测试 |
| `kynet.direct.threadingMode` | `SHARED` | `SHARED` 由应用线程驱动；`DEDICATED` 使用独立 conductor/sender/receiver 线程 |

## Registry 集群

每个 Registry 必须使用稳定且唯一的 `nodeId`，并使用同一个至少 16 字节的集群密钥。节点间发现和 Gossip 仍使用 HMAC-SHA256 认证的 UDP 控制面；服务节点与 Registry 间注册发现使用 Netty TCP。集群协议现为 v4，仅包含发现和目录 Gossip；升级时需同步升级 Registry 集群。客户端数据面使用独立的 MediaDriver，注册中心退出不关闭已建立的数据通道。

示例（PowerShell）：

```powershell
$env:MAVEN_OPTS = "-Dkynet.registry.cluster.enabled=true " +
  "-Dkynet.registry.cluster.name=game-prod " +
  "-Dkynet.registry.cluster.secret=$env:KYNET_CLUSTER_SECRET " +
  "-Dkynet.registry.nodeId=registry-1 " +
  "-Dkynet.registry.clientHost=10.0.1.11 " +
  "-Dkynet.registry.clusterHost=10.0.1.11 " +
  "-Dkynet.registry.clusterBindHost=0.0.0.0 " +
  "-Dkynet.registry.clusterPort=19001 " +
  "-Dkynet.registry.discoveryAddress=10.0.1.255 " +
  "-Dkynet.registry.discoveryPort=18899"
mvn -pl kynet-registry exec:java -Dexec.mainClass="cn.itsub.kynet.registry.RegistryMain"
```

RPC 请求在本地目录中按显式目标或 `sessionId -> userId -> requestId` 选择提供者，相同会话在接收端按串行条带执行。幂等 RPC 使用限次重试与进程内去重；同一调用的重试固定到首次选择的实例及代次。推送与事件入队成功不代表接收端已执行，异步发送超时通过直连丢弃指标报告。

关键业务 RPC 可以显式启用端到端幂等重试：

```java
InvokeOptions options = InvokeOptions.builder()
        .sessionId(sessionId)
        .userId(userId)
        .timeout(Duration.ofSeconds(3))
        .idempotent(true)
        .maxRetries(10)
        .retryBackoff(Duration.ofMillis(100))
        .build();
```

幂等重试始终复用同一个 `requestId`，接收端按调用方实例、进程代次和 requestId 去重。注册连接断线不会终止直连请求；重试也不会自动切换到另一个提供者。普通 RPC 不会自动重试；请求入队后结果未确定时返回 `RESULT_UNKNOWN`。

Provider 去重缓存是有界的进程内保护，只覆盖同一服务实例存活期间的重试。执行中的幂等请求超过 `kynet.rpc.dedup.inFlightTtlMillis` 后会固化为 `IDEMPOTENCY_IN_FLIGHT_TIMEOUT`，迟到结果不能覆盖该终态。背包、交易、发奖、货币等关键写操作仍必须使用业务唯一号，并通过数据库唯一约束、事务记录或共享幂等表实现跨实例、跨重启去重。

每次重注册递增 registration generation，数据面进程 incarnation 在该 ServiceNode 生命周期内保持不变。客户端保留种子 Registry 并发现其他存活 Registry；重新接入时保留旧目录直到收到完整的新快照，再原子替换。

`ServiceNode` 可配置一个或多个种子 Registry。唯一种子暂时不可达时，`start()` 会保留直连数据面并在后台退避重试；已发现的 Registry 地址只保存在进程内，因此单物理种子长期失效时，重启后的冷启动仍需等待它恢复或由稳定 DNS 指向其他节点。`knownRegistryEndpointCount()` 包含保留的种子地址，不等于当前健康节点数。

集群模式下，新 Registry 在初始发现窗口及已知存活节点的路由快照同步完成前，`isReady()` 为 false 且拒绝注册；已就绪节点持续补发带版本的完整 Registry 拓扑。目录是最终一致的：新旧服务短暂不可见或仍可见时，调用方需处理 `NO_PROVIDER`、超时及结果未知。

生产环境至少应显式配置以下属性：

| 属性 | 用途 |
| --- | --- |
| `kynet.registry.cluster.enabled` | 启用集群模式 |
| `kynet.registry.cluster.secret` | 集群共享密钥，至少 16 个 UTF-8 字节 |
| `kynet.registry.nodeId` | 跨重启稳定的唯一节点名 |
| `kynet.registry.clientBindHost` | Registry TCP 注册接入的本地绑定地址，默认 `0.0.0.0` |
| `kynet.registry.clientHost` | 广播给业务客户端的 Registry TCP 地址 |
| `kynet.registry.clusterHost` | 广播给其他 Registry 的集群地址 |
| `kynet.registry.clusterBindHost` | 集群 UDP 监听地址 |
| `kynet.registry.clusterPort` | 每节点唯一的集群 UDP 端口 |
| `kynet.registry.discoveryAddress` | 同网段广播地址或受控发现地址 |
| `kynet.registry.discoveryBindHost` | 发现通道的本地绑定地址，默认 `0.0.0.0` |
| `kynet.registry.discoveryPort` | 集群共同监听的发现端口 |
| `kynet.registry.heartbeatIntervalMs` | 客户端故障探测心跳，默认 250 ms |
| `kynet.registry.reconnectDelayMs` | 断线后的首次重连延迟，默认 100 ms |
| `kynet.registry.maxReconnectDelayMs` | 重连退避上限，默认 5,000 ms |
| `kynet.registry.joinGraceMs` | 集群新节点初始发现窗口，默认至少两个发现周期且不少于 200 ms |
| `kynet.registry.topologyRefreshMs` | 完整 Registry 拓扑周期补发间隔，默认 5,000 ms |
| `kynet.registry.connectTimeoutMs` | Registry TCP 建连超时，默认 1,000 ms |
| `kynet.registry.clientQueueBytes` | 客户端注册控制消息待发送字节上限，默认 1 MiB |
| `kynet.registry.sessionBufferBytes` | Registry 每连接控制消息缓冲上限，默认 256 KiB |
| `kynet.rpc.dedup.maxEntries` | 单个 Provider 的幂等响应缓存上限，默认 100,000 |
| `kynet.rpc.dedup.ttlMillis` | 已完成幂等响应的缓存时间，默认 60,000 ms；应大于调用方最大重试窗口 |
| `kynet.rpc.dedup.inFlightTtlMillis` | 执行中幂等请求的最长占用时间，默认 30,000 ms；应大于业务 action 的正常最长耗时 |

Registry 使用单一 TCP 注册控制入口。业务直连参数见前述部署文档；Registry 集群继续使用 UDP 发现机制，业务节点之间使用注册的独立直连端点。旧的 `kynet.broker.*` 配置键仍可作为回退，优先使用 `kynet.registry.*`。

`RegistryServer.clusterMetrics()` 提供成员状态、待组装目录快照、Gossip 发送失败和认证重放拒绝指标。`RegistryServer.registryMetrics()` 提供注册实例数、累计注册次数、控制消息发送/缓冲/背压及拒绝消息计数。发往 Registry 的业务帧会被拒绝，不存在业务转发、广播扇出或 ACK 重试通道。

历史转发架构的测试计划和结果见 [Broker 集群单机多 JVM 资格测试报告](docs/broker-cluster-qualification-report-2026-08-07.md)。其吞吐和内存结果不能直接作为当前直连架构的容量依据。

## Gateway 外网加固

安全端点必须配置证书和私钥：

```java
GatewayServer server = new GatewayServer(
        brokerClient,
        "tcps://0.0.0.0:30001",
        "wss://0.0.0.0:30003/ws"
);
server.setTlsConfig(GatewayTlsConfig.of(
        "/etc/kynet/tls/fullchain.pem",
        "/etc/kynet/tls/private-key.pem",
        System.getenv("KYNET_GATEWAY_KEY_PASSWORD")
));
server.setRequestAuthenticator(applicationAuthenticator);
```

`GatewayServer` 不做任何 setter 调用时即使用以下默认值：

| 类别 | 默认值 |
| --- | --- |
| 请求 QPS | 每玩家 `1,000`，每 IP `20,000`，每用户 `2,000`，每 Action `50,000` |
| 连接保护 | 总连接 `100,000`，每 IP `1,000`，每 IP 每秒新建 `200` |
| Session | 空闲超时 `300` 秒 |
| 入站数据 | 帧 `1 MiB`，payload `512 KiB`，字符串 `8 KiB` |
| 下行背压 | 写水位 `128/512 KiB`，待写 `4 MiB/2,000 条`，持续不可写 `5 秒`，策略 `BUFFER` |

上述值都可通过 setter 覆盖；QPS 和连接类上限显式设为 `0` 表示关闭对应限制。`BUFFER` 只允许在硬上限内短暂缓冲，超限或超时后会断开连接；`DROP` 在 Channel 不可写时丢弃新下行包；`CLOSE` 则立即断开。UDP 不具有 TCP 式的单 Peer 接收背压，Socket 不可写时直接丢弃当前 Datagram。

Registry 连接和至少一个 Gateway 监听端点是启动所必需的部署信息，必须在创建 `GatewayServer` 时传入。框架无法为 TLS 证书与私钥、Token/登录鉴权、Action 访问控制和业务 `UserHook` 提供通用值，这些应由应用显式配置。未配置 `GatewayRequestAuthenticator` 时会允许所有请求，公网部署应实现业务认证。WebSocket 默认允许所有 Origin；只有当浏览器依赖 Cookie 等可被跨站携带的凭据时，才需要按项目调用 `setAllowedWebSocketOrigins` 增加来源白名单。推送回调 `GatewayPushHandler` 只用于业务观测或扩展，可不配置。

## 服务端权威踢人

踢人是框架内部控制帧（`GATEWAY_KICK`），不是普通推送：网关收到后注销会话并关闭连接，`UserHook.quit` 照常触发，连接配额同步释放，累计次数见 `GatewayRuntime.kickedConnectionCount()`。

```java
// action 内断开当前玩家
context.kickSelf("违规发言");
// 顶号：登录成功后踢掉同账号旧连接，保留当前会话
context.kickOtherSessions(userId, "账号在其他设备登录");
// 封号：踢掉该用户当前所有连接（含各设备）
context.kickUser(userId, "banned");
// 任意代码处（管理后台等），按 sessionId 精确踢
serviceNode.kickSession(sessionId, "gm kick");
```

需要给玩家发下线提示时，先 `pushToGateway`/`broadcastSelf` 发一条业务消息，再调用 kick。踢人帧与推送共用同一条定向/扇出路由：已知承载网关时精准投递，否则扇出全部网关、由各网关本地解析。踢下线不依赖客户端配合，客户端表现为连接被服务端关闭。

## 运行方式

前提：本机安装并启用 Java 25 与 Maven。

Java 25 下运行基于 Aeron/Agrona 的进程时，需要开放 `jdk.internal.misc` 给未命名模块访问。

- 使用 Maven 启动时，仓库中的 `.mvn/jvm.config` 已自动添加 `--add-exports=java.base/jdk.internal.misc=ALL-UNNAMED`。
- 如果直接在 IntelliJ IDEA 里运行 `main` 方法，请在 Run Configuration 的 VM options 中手动添加同样的参数。

1. 启动 Registry：

```bash
mvn -pl kynet-registry exec:java -Dexec.mainClass="cn.itsub.kynet.registry.RegistryMain"
```

2. 启动登录服务示例：

```bash
mvn -pl examples/example-login-service exec:java -Dexec.mainClass="cn.itsub.game.login.LoginApplication"
```

3. 启动网关示例：

```bash
mvn -pl examples/example-gateway exec:java -Dexec.mainClass="game.external.GatewayServerApp"
```

## 示例模块

- `examples/example-login-service`：Action 服务示例
- `examples/example-gateway`：网关接入与推送示例
- `examples/example-rpc-action-call`：RPC 与直连压测示例

说明：

- RegistryMain 监听 Netty TCP 注册连接，不启动注册用的 MediaDriver；每个 ServiceNode 独立启动直连数据面的 MediaDriver。业务直连同机优先使用 IPC，不可用时使用 UDP。
- 这里的 host:port 表示 Registry 的 TCP 注册端点，默认 127.0.0.1:8888。
- 直连数据面的 UDP 端口默认自动分配，需保证对其他服务可达。

## 与规划文档的差距

当前仍未覆盖：

- 跨网段的 Registry 自动发现，以及经过大规模生产验证的成熟集群控制面
- KCP 协议接入
- 完整会话路由、鉴权、限流与在线管理
- 内置 Prometheus/Micrometer 导出器、熔断和序列化插件化

当前框架采用“Registry TCP 注册发现 + ServiceNode Aeron 直连 + Action 接入模型”。
